Workspace Intelligence Screen Inventory and UX Review

A redesign report covering the intelligence area only: its navigation, primary destinations, activity workspace, panels, agent lifecycle, setup and policy. Workflows, processes, tools and administration are excluded.

Main findingNew instructionScreen inventoryTarget structureScreen critiquesScreenshotsDelivery plan

The sidebar improved the frame. The screens still need a shared work model.

Workspace Intelligence still combines an activity log, a chat application, agent administration and setup forms. Reusing good library components has not, by itself, created a coherent experience.

The sidebar should remain. Redesign the compositions behind it around a complete unit of work: objective, executor, evidence, progress, decision and outcome. Keep chat as one interaction within work; retain structured decisions, visual artifacts and diagnostic receipts as first-class parts of the same activity.

P1 means confusion affects a core user decision or work flow; P2 means hierarchy, discoverability or efficiency needs improvement. These are UX priorities, not security severities. Every inventory item has a proposed redesign; this report does not authorize or apply those changes.

  1. One vocabulary is missing. Instruction, session, conversation, run and activity name different layers without explaining the relationship.
  2. Work identity is weak. A selected activity is titled by its enclosing session; goal, executor, evidence and outcome are not consistently visible together.
  3. Creation is still a blank chat. New instruction does not explain what will be created or who will act.
  4. Review is too document-heavy. Important ontology and process changes are reviewed through prose, counts and JSON rather than their domain structure.
  5. Configuration forms need recomposition. Truncated labels and flat tool/resource lists make authority and runtime limits hard to inspect.
  6. State communication is fragmented. Saved policy, readiness, running work, pending decisions and recovered failures need distinct treatments.

What New instruction actually does

It navigates to /intelligence?view=conversation and opens an empty conversation draft. That click alone does not start execution. Sending text creates a session if required and submits a goal with selected evidence through the existing request path.

Recommendation: replace it with New activity. The destination should be a work-creation brief showing goal, executor, evidence and expected outcome. “Instruction” can remain the label for the user’s input inside that brief. “Session” can remain a technical/history grouping; “run” should mean an execution attempt or diagnostic execution record.

Product termMeaning
ActivityA bounded unit of requested or suggested work, with an objective, state and outcome.
AssignmentAn activity offered to a named executor with context and success criteria.
AgentThe configured executor; distinguish the workspace coordinator from specialists.
EvidenceThe authorized and selected saved revisions used for work; distinguish inventory from grants.
DecisionA structured question, approval or review that requires a user action.
RunThe execution record and receipts for work, shown mainly in diagnostics.
SessionA retained history/context grouping that may contain several activities.

Proposed structure

DestinationMain user questionContents and primary action
OverviewWhat does this workspace understand, and what needs my attention?Purpose, readiness, coverage/gaps, pending decisions, recent outcomes. Contextual setup or review action.
ActivitiesWhat work is happening or has happened?Searchable/filterable work inbox. New activity.
SuggestionsWhat useful work is the agent proposing?Triage and evidence-backed assignment review. Acceptance links to resulting activity.
AgentsWho can perform work, with what responsibilities and authority?Coordinator and specialist roster, record configuration, publication and operating state.
Workspace setupHow is the workspace understanding established and maintained?Purpose, evidence selection, inspection, coverage review, configuration acceptance and setup history.
Workspace policyWhat may run, which provider may be used, and under which limits?Consistently named policy surface, readiness summary and links to automation rules.
Activity detail has one identity. Keep goal, executor, state and target in a persistent header. Present result and decisions as the main content; evidence and execution diagnostics are contextual panes. A transcript supports the work record. Do not force every activity to look like an ongoing chat.

Use the licensed AppSidebar, ChatLayout, AgentList, AgentSummary, AgentCreate, GenerativeForm, AgentGate, KnowledgeSources, AttachmentsTray, ContextWindow, ThinkingState, AgentRunTree, TraceViewer, RunLog and ArtifactPanel as appropriate. Inspect each component’s source and real preview before adapting it. Host-level composition is necessary; replacement primitives and a second agent runtime are not.

Screen by screen critique

WI01 · Shared surface · Browser and source

Navigation and shared frame P1

All intelligence routes

Critique

The App Sidebar gives the area a clear frame. However, its session-history section appears only in the instruction/detail view. That view highlights Activities while its title says Workspace intelligence and its tab names a session. The workspace name is routinely truncated. Lifecycle styles still target .wi-lifecycle, which the new IntelligenceShell no longer mounts; rounded cards and inconsistent sizing have reappeared.

User impact. Navigation changes shape as the user moves through one task, and the visual system varies between destinations.

Redesign direction

Keep the licensed sidebar. Use a stable work navigation, meaningful page titles and breadcrumbs, and one documented style adapter. Move session history out of the global rail. Restore the intended styles through the actual shell scope, rather than adding more unrelated overrides.

Reuse. AppSidebar, ChatLayout, shared FullscreenWorkbench, official Untitled UI controls

Acceptance. Every destination has a clear selected item and title; collapse and mobile overlay remain usable; no orphaned host selectors; 15–16px body text and readable secondary labels.

WI05 · Work creation screen · Browser and source

New instruction P1

Sidebar New instruction → ?view=conversation

Critique

This opens a blank conversation draft, New session tab, starter prompts and composer. Clicking it alone does not enqueue work; sending creates a session if needed and submits a goal. The screen does not identify an executor or make scope and expected outcome explicit. Read only is a starter label, not an independently visible execution contract.

WI06 · Work detail screen · Browser and source

Activity detail and completed result P1

Open a row in Activities

Critique

A selected work item is still presented under a session title such as explain this workspace. The actual goal is only a message in the transcript. The completed sample asks an A/B/C/D question in prose, while the activity is marked Completed. A persistent composer does not distinguish answering a pending interaction from starting follow-up work.

User impact. The identity and outcome of the activity are difficult to understand; a question can look actionable without any structured pending interaction.

Use the activity goal as the title, with executor, status, target and outcome summary. Separate result, decisions and execution detail. Keep the transcript as supporting history. Distinguish Reply to a recorded question from Create follow-up activity. Do not retroactively fabricate pending forms from historical prose.

Reuse. ThreadHeader, ChatThread/ChatScreen as supporting content, ArtifactPanel, AgentGate

Acceptance. Opening any historical row shows its own goal and receipts; state and next action agree; history stays readable without confusing a new request with a resume.

Session history and archive management P2

Active/Archived session section in activity detail

Critique

Session history is nested under primary workspace navigation and appears only in the workbench. A session title can cover multiple distinct activities. Archive/delete belong to that session while users are browsing individual work items. The distinction between closing a tab, archiving history and deleting history is easy to miss.

User impact. Users can lose their place or misunderstand the scope of a history action.

Redesign direction

Keep activity navigation primary. Place related sessions in a clearly named secondary history view or contextual section. Explain archive as hiding history and delete eligibility as no workspace modifications. Preserve the backend modification-based deletion guard.

Reuse. SessionList, SessionTabs only where useful, official contextual menus

Acceptance. Close, archive, restore and delete have distinct wording and scope; ineligible deletion explains why; archive never implies cancellation or rollback.

Acceptance. Users can discover whether automatic review is on, what triggers it, its budget and what is pending; enabling a rule does not imply automatic acceptance of suggestions.

Redesign delivery order

  1. Agree on the work model and frame. Define Activity, Assignment, Agent, Evidence, Decision and Run; specify header, sidebar, typography, spacing, control geometry and scroll ownership. Resolve the missing lifecycle style scope. Produce representative screen compositions before implementation.
  2. Redesign the primary work path. Activities inbox → New activity brief → active work → question/decision → completed outcome. Include failure, uncertain outcome and reconnecting states in the same design pass.
  3. Redesign context and review. One attachment entry with clear saved-knowledge/upload choices; searchable revision selection; ontology and process review using existing domain renderers; explicit apply outcomes.
  4. Redesign the agent lifecycle. Roster → create → edit → publish → enable/pause/archive, with tools and knowledge grants readable before approval.
  5. Redesign setup, automation and policy. Evidence-driven setup stages, coverage/gap review, activation consequences, automatic-review discoverability and truthful readiness.
  6. Validate the whole flow. Desktop, compact overlay and keyboard; owner/admin/editor/viewer permissions; large resource inventories; structured questions; stale proposals; no telemetry; archived histories; recovered failures and uncertain mutations.

Definition of done for every redesigned surface

  • One clear purpose, identity and primary action, with consistent terminology.
  • Licensed components are composed deliberately; original source and provenance remain preserved.
  • No truncated decision-critical labels, tiny controls, empty telemetry columns or decorative controls with no task purpose.
  • Header and navigation remain stable; the correct bounded content area scrolls; important actions stay reachable.
  • Loading, empty, error, restricted, pending and success states have useful next actions.
  • Execution state, publication state, saved policy and workspace modifications remain distinct and truthful.
  • Inspect screenshots of the real implementation against the approved composition before calling it complete.
